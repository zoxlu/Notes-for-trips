# CLAUDE.md — 名古屋家族旅行 Vault 維護規則

你是這個 Obsidian vault 的維護者。你的工作是把 `raw/` 裡的原始素材，整理成 `wiki/` 裡結構化、家人容易瀏覽的筆記，並在需要時把篩選好的內容整理進 `outputs/`。

## 資料夾角色

- `raw/` — **只增不改**。使用者會把 LINE 上家人分享的文字、截圖描述、網頁存檔、YouTube 連結貼進這裡，檔名建議 `YYYY-MM-DD-來源簡述.md`。你只能讀取，絕對不要編輯或刪除這裡的檔案。
- `wiki/` — 你產出的結構化筆記，是家人主要瀏覽的地方。
- `wiki/1.分類瀏覽/` — 給人看的「篩選頁」，用**寫死的清單**（不是 Dataview query），確保之後不管在 Obsidian 或發布成網站都能正常顯示。
- `wiki/7.繃皮/` — 每位家人各自的個人分享頁，見下方「個人分享頁」規則。
- `outputs/` — 排定行程後才會用到的產出（每日行程、預算表）。9-10月之前這裡通常是空的，不用主動處理。
- `wiki/04-Attachments/` — 圖片、截圖（已搬進 wiki/ 底下，確保能被 Quartz 正確引用）

## Map View（地圖瀏覽）

家人如果想用地圖方式瀏覽所有景點/美食/住宿，需要在 Obsidian 裝 **Map View** 這個 community plugin（搜尋 "Map View" 安裝即可）。它會自動讀取每則筆記 frontmatter 裡的 `location: 緯度,經度` 欄位，把所有有座標的筆記顯示成地圖上的點，不需要額外設定。

## 每次執行的標準流程

1. 掃描 `raw/` 中還沒被處理過的檔案（可以在檔名或內容找 `<!-- processed -->` 標記判斷是否已處理，處理完在對應 raw 檔案結尾加上這個標記，但不修改其他內容）。
2. 如果素材裡包含 YouTube 連結（`youtube.com` 或 `youtu.be`），用 `yt-dlp` 抓取逐字稿（不要用 youtube-transcript 類的 MCP，這類套件目前普遍會被 YouTube 擋掉）：
    
    ```bash
    yt-dlp --write-auto-sub --skip-download --sub-lang en,ja,zh-Hant,zh-Hans "<影片網址>"
    ```
    
    語言代碼列多個，抓到哪個算哪個。抓到的 `.vtt` 字幕檔直接讀取內容判斷這支影片跟哪些景點/美食/住宿/活動有關，讀完後把暫存的 `.vtt` 檔案刪除，不要留在 repo 裡。如果 `yt-dlp` 沒裝、抓取失敗，或影片完全沒有任何語言的字幕，在該筆記加註「⚠️ 無法取得逐字稿，需使用者手動補充」，不要憑影片標題臆測內容。
3. 針對每個素材，判斷類型：`place`（景點/商店，包含健行、吉卜力公園等活動類素材）、`food`（餐廳/美食）、`transport`（交通）、`accommodation`（住宿）。`activity` 類型已停用，活動類素材一律歸類為 `place`，並依內容挑選合適的 `place_category`。一支影片或一篇文章可能同時提到多個地點，需要拆成多則筆記，並在每則筆記的來源註明是同一部影片的哪個段落（可用時間戳記）。
4. 每則筆記的 _原始連結備註_ 這個區塊放上 `raw/` 來源檔案的 wikilink，並把該檔案裡面文字敘述部份到這裡（詳細格式見下方「原始連結備註」章節）。
5. **提取「武林秘笈」內容**：素材裡如果有跟這個地點/店家相關、但不屬於 schema 制式欄位的實用資訊或小知識（例如「這家的三明治放40分鐘還是酥脆」「這間飯店電梯可以直通地下捷運」），整理進筆記的「## 🗝️ 武林秘笈」區塊（詳細格式見下方「武林秘笈」章節）。如果素材裡沒有這類資訊，這個區塊留空或略過，不用勉強湊內容。
6. 檢查 `wiki/` 對應資料夾裡是否已經有同一個地點/店家的筆記（比對標題、別名、地址），**避免重複建立**。
    1. 如果已存在：
        - 資訊一致 → 合併補充進現有筆記，並在筆記底部的「原始連結備註」區塊加一行來源，**同時把這個 raw 檔案加進 frontmatter 的 `raw_note` 陣列**（如果還沒有的話；已存在就不重複加）。更新時務必保留 `## 📝 我的備註` 區塊原樣不動。
        - 資訊衝突（例如營業時間、價格不同）→ **不要覆蓋**，在筆記加一個「⚠️ 待確認」callout 區塊，把兩邊資訊都列出來並註明各自來源和分享者。
        - 如果 `location` 或是 `image` 已經有資料，則**不必**重複執行座標或代表圖片的填寫任務。
    2. 如果沒有衝突、是新項目 → 依照下面的 schema 建立新筆記。新增筆記時，內文開頭不要寫 `# {{title}}` 這一行，Quartz 會自動從 frontmatter 的 title 產生標題並固定在頁面頂部，內文重複寫一次會造成標題顯示兩次。
7. **官方網站**：處理素材時，主動搜尋這個地點/店家的官方網站，填入 `official_url`。找不到的話留空，不要憑猜測填一個不確定的網址。
8. **來源描述**：依 `source_url` 的內容判斷一句簡短描述填入 `source_label`（跟「資訊來源清單」的描述邏輯一致），例如部落格名稱、網站名稱。
9. **交叉連結（雙向檢查，避免全庫兩兩比對拖慢速度）**： - 檢查這批新增/更新的筆記內文（不含 frontmatter），如果提到了 `wiki/` 裡其他任何筆記的**標題**或 **`aliases`** 裡列出的別名、且目前還不是 wikilink 形式，把它轉成 `[[該筆記標題]]` - 反過來，也要檢查 `wiki/` 裡**所有既有筆記**的內文，如果提到了這批新增/更新筆記的標題或別名、且還不是 wikilink，一樣要補上連結（這樣才能處理「舊筆記提到新筆記」的情況） - 只比對標題和明確列出的 `aliases`，**不要**自己發明關鍵字或憑語意猜測要連結什麼，避免把單純提到地名/人名當背景描述的句子過度連結，影響閱讀體驗 - 不要修改 `## 📝 我的備註` 區塊裡的內容 - **主動補充 `aliases`**：處理素材時，如果發現同一個地點/人物有多種常見稱呼（例如車站全名 vs 簡稱、店名的中日文版本、家人習慣用的暱稱），主動幫對應筆記的 `aliases` 補上，不用等使用者要求。既有筆記如果因為這次新素材而發現了新的別名寫法，也要一併補上該筆記的 `aliases`，這樣往後才能持續被交叉連結正確比對到。
10. 全部處理完後，**重新產生** `wiki/1.分類瀏覽/` 底下所有 index 頁面、`wiki/7.繃皮/` 底下所有個人分享頁（見下方規則），確保連結清單是最新的。
11. 在回覆使用者時，簡短列出這次新增/更新了哪些筆記、交叉連結加了幾個、以及有沒有發現待確認的衝突。
12. **圖片檔名一致性檢查**：這批處理完的筆記，如果引用了 `04-Attachments/` 裡的本機圖片，檢查該筆記裡所有提到這個檔名的地方（`image` 欄位、內文嵌入語法等）是否完全一致，也確認檔名本身沒有空格。不一致或有空格的話，統一修正。

## 筆記 Schema（YAML frontmatter）

所有類型共用欄位：

```yaml
---
title:
type:              # place / food / transport / accommodation
region:             # nagoya-city / transit
station:            # 最近地鐵站或車站，例如：名古屋站 / 榮站 / 藤が丘站 / 南木曽駅
district:           # 商圈/區域，例如：榮、大須、妻籠宿、馬籠宿
location:           # 經緯度，格式 lat,lng（例如 35.1709,136.8815），給 Obsidian Map View plugin 用，也可轉 Google Maps 連結。transport 類型可略過（起訖點不是單一座標）
image:              # 代表圖，見下方「代表圖片怎麼抓」規則
image_source:       # 圖片來源說明，例如「家人截圖」或官網網址
status: researching # researching / shortlisted / confirmed / rejected
priority: nice-to-have  # must / nice-to-have / optional
shared_by:          # 誰在 LINE 分享的
raw_note: []       #來源是 /raw資料夾 的哪些 note，用陣列記錄所有曾經提供過這則筆記資訊的來源檔案（同一個地點可能被多個 raw 檔案分別提到）
source_url:
official_url:       # 官方網站網址，處理素材時主動搜尋這個地點/店家的官網並填入
source_label:       # source_url 的簡短可讀描述，例如「波比看世界的名古屋旅遊攻略部落格」，格式跟「資訊來源清單」裡的描述方式一致
date_added:
day_assigned:       # 9-10月排行程時才填，例如 Day2
tags: []
aliases: []        # 這個地點/人物的其他常見稱呼，供交叉連結比對用，例如「大須觀音」的 aliases 可以是 [大須觀音站]
興致指數: # 0-5 這部份由使用者手動填寫
---
```

額外欄位（依類型）：

- `place` 專用：`duration`（大概會花的時間，例如「1.5小時」）、`opening_hours`（營業/開放時間）、`place_category`（可多選，允許值：文化古蹟 / 逛街尋寶 / 自然漫步 / 知性趣味）
- `food` 專用：`meal_slot`（breakfast / lunch / dinner / snack）、`cuisine`、`price_range`、`booking_required`、`opening_hours`、`food_category`（可多選，允許值：名古屋鄉土限定 / 美食名店 / 點心輕食 / 必吃清單）
- `accommodation` 專用：`nights`、`price_per_night`、`meal_plan`、`onsen`
- `transport` 專用：`transport_mode`、`route_from`、`route_to`、`duration`、`cost`

### 子分類判斷原則（`place_category` / `food_category`）

- 處理新的 `place` 筆記時，主動判斷屬於哪些 `place_category`（可多選），依內容特性掛標籤，不要求恰好一個。
- 處理新的 `food` 筆記時，主動判斷屬於哪些 `food_category`；「必吃清單」僅用於總覽/清單型文章（非單一店家筆記），可與其他子分類並存。
- `activity` 類型已停用，未來如有活動類素材，一律歸類為 `place` 並視內容挑選合適的 `place_category`。

#### `place_category` 四個值的定義

- **文化古蹟**：神社寺廟、城堡、傳統老街、歷史建築、美術館/博物館等偏歷史文化性質的景點
- **逛街尋寶**：商店街、購物中心、市場、暢貨中心等以逛街購物為主的地點
- **自然漫步**：庭園、公園等以戶外散步、賞景為主的地點
- **知性趣味**：科學館、水族館、主題樂園、產業紀念館等體驗型/教育型/寓教於樂的設施

這四個分類彼此不互斥，複合型景點（例如同時有博物館、庭園、購物區的設施）可以視內容掛多個，不用只選一個。判斷有疑義時，依景點**主要吸引力**來源決定要不要多掛，不用勉強每個面向都掛滿。

#### `food_category` 四個值的定義與互斥規則

- **名古屋鄉土限定**：料理本身是名古屋當地發源或特有的鄉土料理（例如味噌豬排、鰻魚飯、雞翅、味噌煮、外郎、小雞布丁等名古屋才有的品項）
- **美食名店**：不屬於名古屋鄉土料理，但本身是知名或值得專程造訪的餐廳（例如螃蟹、居酒屋、壽司、拉麵等一般美食類型裡的名店）
- **點心輕食**：甜點、麵包、輕食、咖啡廳類，不分是否為鄉土限定
- **必吃清單**：僅用於總覽/清單型文章（例如「必買伴手禮」「7大必吃」這種文章本身），不用於單一店家筆記

**互斥規則**：「名古屋鄉土限定」與「美食名店」互斥，一則筆記只會歸類到其中一個，不會同時掛兩者——判斷依據是「這道料理/這家店賣的東西，是不是名古屋當地特有的鄉土料理」，是則歸鄉土限定，不是則歸美食名店。「點心輕食」則不受此限，可以跟「名古屋鄉土限定」或「美食名店」其中一個並存（例如小雞布丁蛋糕同時是鄉土限定+點心輕食）。「必吃清單」也可以跟前三者之一並存，依總覽文章實際內容判斷。

若素材來源是 YouTube 影片，`source_url` 直接填影片網址，若能定位到具體時間段，用 `#t=分:秒` 附加在網址後面（例如 `https://youtu.be/xxxxx#t=3:20`），方便日後回去對照原始影片。

### 座標（`location`）怎麼填

- `place`、`food`、`accommodation` 都要盡量填 `location`；`transport` 因為是起訖點的移動，通常留空即可。
- 座標優先順序：素材裡如果附了 Google Maps 連結，直接從連結解析出經緯度；沒有的話，用你能存取的工具（web search / web fetch）查詢該地點的經緯度，格式統一為 `緯度,經度`（decimal degrees，例如 `35.1709,136.8815`），不要用度分秒格式。
- 查不到精確座標時，`location` 留空，並在筆記的「待確認」區塊註明「座標待補」，不要憑印象亂填，錯誤座標比沒有座標更麻煩。
- Google Maps 連結現在會自動顯示在筆記上方的 property 區塊，**不要**再於筆記內文（`## 簡介` 底下）額外寫一行 Google Maps 連結，避免重複顯示兩次。

### 代表圖片（`image`）怎麼抓

按以下優先順序，選第一個能用的來源，不要跳著選：

1. **家人分享的截圖/照片**：如果這則筆記對應的 raw/ 素材裡有截圖（存在 `04-Attachments/`），優先用這張，`image` 填 `04-Attachments/檔名`，`image_source` 填「家人截圖」。
2. **官網代表圖片**：素材裡的 `source_url` 如果是該地點的官網，google map裡的照片，或可信賴的旅遊網站，且頁面有清楚的代表照片（例如 og:image、首頁大圖），用該圖片的**完整外部網址**（不要下載存到 vault 裡），`image_source` 填圖片來源的網域（例如「來自官網 taoya.jp」）。
3. **兩者都沒有**：`image` 留空，在筆記的「待確認」區塊加一行「圖片待補」，不要用搜尋隨便找一張視覺上像的圖片湊數，也不要用其他地點的照片代替。

筆記內容裡的嵌入語法：

- 本機圖片（情況1）：`![[wiki/04-Attachments/檔名]]`
- 外部連結圖片（情況2）：`![代表圖](完整圖片網址)`

嵌入位置統一放在「## 簡介」標題下方。

#### 檔名規範（避免空格造成連結失效）

`04-Attachments/` 底下的檔名，一律**不能包含空格**——Quartz 產生網址時會把空格轉成連字號，如果實際檔名還是空格，連結會對不上而 404。

- 如果素材是使用者直接貼截圖進 Obsidian，Obsidian 預設可能會產生帶空格的檔名（例如 `Pasted image 20260718233124.png`），處理素材時如果遇到這種檔名，**先把檔案改名**成連字號版本（例如 `Pasted-image-20260718233124.png`），再繼續後續步驟。
- 一張圖片可能同時被三個地方引用：`image` frontmatter 欄位、`raw_note` frontmatter 欄位（如果剛好也指到同一張圖）、內文的 `![[...]]` 嵌入語法。**改檔名之後，這三處只要提到這張圖，都要同步改成新檔名，不能只改其中一兩處。**

**發布網站時的注意事項**：如果之後用 Quartz 之類的工具把 `wiki/` 發布成網站，情況2的外部連結圖片本質上是連到別人網站的圖床，一般私人分享沒問題，但如果使用者說要公開分享給更多人，要主動提醒他考慮把這類圖片拿掉，只保留家人自己拍的照片（情況1）。

### 「原始連結備註」區塊格式（重要，不要跟 `source_url` 搞混）

每則筆記的「原始連結備註」區塊，是連回 `raw/` 素材本身的記錄，跟 frontmatter 裡的 `source_url`（外部網址，官網/網頁連結）是**兩個不同用途、不要混用**：

- - **第一行**：用純文字寫出 `raw/` 裡對應的來源檔案名稱（不要用 `[[...]]` wikilink 語法），格式：`來源檔案：檔名`，例如 `來源檔案：2026-07-20 波比 繃皮蛇`。這裡故意不用 wikilink，因為 `raw/` 不會同步進 Quartz 網站，wikilink 在網站上會變成死連結；純文字檔名在 Obsidian 跟網站上顯示效果一致，都不能點但不會有死連結問題。
- **接著**：空一行，然後把該 raw 檔案裡的文字段落，**原文複製貼上**進來，前面加上分享人（`shared_by`）和冒號（：），用引用格式（每行前面加 `>`）
- 如果一則筆記的資訊來自**多個** raw 檔案（例如同一個地點被家人分別分享過兩次），每個來源各自一組「wikilink + 分享人＋引用文字」，換行，中間用空行分隔

範例：

```markdown
## 原始連結備註
> 來源檔案：2026-07-20 波比 繃皮蛇、
> 
> 波比：（原始素材無文字內容，只有截圖）...。
```

如果有第二個來源：

```markdown
## 原始連結備註
> 來源檔案：2026-07-20 波比 繃皮蛇
>
```

### 「武林秘笈」區塊格式（`## 🗝️ 武林秘笈`）

這個區塊放的是**跟這個地點/店家有關、但不屬於任何 schema 欄位的實用資訊或小知識**， 例如食物的口感特性、交通轉乘的小訣竅、排隊/現場動線的提醒、省錢妙招、歷史緣由、特色推薦等。跟其他區塊的分工：

- 跟「## 📝 我的備註」不同：那個區塊完全屬於使用者自己的空間，你不能修改；「武林秘笈」 是你依素材內容主動整理的，你可以新增
- 跟「原始連結備註」不同：那個區塊是**完整保留**家人分享的原始文字（逐字引用）； 「武林秘笈」則是**你消化過、提煉出重點**的精簡條列，不是逐字複製

**格式**：

```markdown
## 🗝️ 武林秘笈
- 三明治外酥內軟，就算坐車放了40分鐘還是很美味（部落格：波比看世界）
- 搭電梯到1樓需要轉乘，但電梯可以直通地下1樓，轉乘捷運很方便（家人分享）
```

- 每條一行，條列式，句尾用括號註明來源：家人分享的寫「（家人分享）」或直接寫分享人 暱稱「（波比分享）」；部落格/網站來源寫「（部落格：網站名稱）」或「（網站：xxx）」
- **疊加式累積，不要整份重寫**：這個區塊跟「原始連結備註」一樣，每次處理新素材如果 發現新的武林秘笈，用新增一行的方式疊加進去，不要把既有的內容整個換掉或重新改寫
- **避免逐字照抄部落格原文**：如果來源是外部部落格文章，一律用自己的話重新精簡摘要， 不要整句原文照搬（版權考量），跟「原始連結備註」允許逐字引用家人分享文字的規則不同 ——「原始連結備註」引用的是家人自己的文字，「武林秘笈」如果來自外部網站就要改寫
- 內容要**具體、實用或是有知識性、趣味性**，以「值不值得告訴一個第一次去的人」為判斷標準
- 如果同一則筆記已經有相同或高度重複的武林秘笈，不要重複新增一行，除非新資訊補充了 更多細節（例如原本只寫「早餐好吃」，新素材具體寫出「早餐的鰻魚飯三吃份量足夠2人分」， 這種情況可以把原本籠統的一行換成更具體的新版本）
- 若這則筆記目前沒有任何值得收錄的武林秘笈，這個區塊可以留空或整段不建立，不用勉強湊字數

**位置**：放在「## 簡介」之後、「⚠️ 待確認」callout（如果這則筆記有的話）之前， 「⚠️ 待確認」之後接著才是「原始連結備註」。也就是整體順序為：簡介 → 武林秘笈 → 待確認（如果有）→ 原始連結備註。

## Index 頁面規則（`wiki/1.分類瀏覽/`）

以下每個檔案都要在你處理完 raw/ 後**整份重寫**（不是增量修改），內容是分組好的 wikilink 清單，方便家人直接點：

- `Home.md` — 入口頁，簡短說明 + 連到以下所有 index
- `By-Station.md` — 依 `station` 分組，每個站名一個 `##` 標題，底下列出所有相關筆記連結
- `By-District.md` — 依 `district` 分組
- `By-Meal.md` — 只列 `type: food` 的筆記，依 `meal_slot` 分組（早餐/午餐/晚餐/點心）
- `By-Type.md` — 依 `type` 分組（景點/美食/交通/住宿）；`place` 與 `food` 底下再依 `place_category` / `food_category` 各自細分小節（子分類是疊加式的，同一則筆記可能同時出現在多個子分類小節底下）
- `By-Status.md` — 依 `status` 分組，方便使用者自己追蹤還有哪些在 researching 階段
- `By-Interest.md` — 依 `興致指數` frontmatter 分組（0 到 5 分，從五分開始往下排，沒有填寫這個欄位的筆記歸類到「未評分」區塊，不要跳過不列）
- `資訊來源清單.md` — 掃描 `raw/` 裡所有已處理過的素材，把每個素材本身附的原始連結（YouTube 影片、部落格、一般網頁）列出來，依連結類型分組：「影片」「部落格」「其他網頁連結」。每個連結前面加一句簡短描述，依該 raw 檔案的標題或內容判斷（例如「波比的名古屋部落格」），格式：`- [簡短描述](原始連結網址)`。判斷「部落格」還是「其他網頁連結」不用太糾結，依內容大致感覺歸類即可；YouTube 連結一律歸「影片」。這份清單連的是**外部原始網址**，不是 `raw/` 檔案本身的 wikilink（`raw/` 不會同步進網站，連 wikilink 過去會是死連結）。

每個清單項目建議格式：`- [[筆記標題]] — 一句話摘要（district, priority）`

## 個人分享頁（`wiki/7.繃皮/`）

每位家人各自一個檔案（例如 `繃皮蛇.md`），檔名對應該人在 `shared_by` 欄位裡使用的暱稱。內容依 `type` 分組，列出所有 `shared_by` 提到這個人的筆記 wikilink。

**不要**在這裡放 `raw/` 檔案的連結——`raw/` 不會同步進 Quartz 網站，這類連結在 Obsidian 裡點得開，但發布到網站上會是死連結，家人瀏覽體驗不好。

這些檔案跟 `wiki/1.分類瀏覽/` 底下的 index 頁面一樣，每次處理完新素材都要**整份重寫**（不是增量修改），不要手動局部編輯造成格式漂移。如果出現一個 `shared_by` 裡的新暱稱、目前還沒有對應的個人分享頁，主動建立一個新檔案。

## 排行程階段（約 2026年9-10月）

當使用者說類似「開始排行程」「整理成每日行程」時：

1. 統計 `wiki/` 裡所有 `status: confirmed` 的筆記
2. 依 `region`（先 nagoya-city 再 kiso-valley）、地理位置相近程度、`priority` 分配到 Day1-Day7
3. 在 `outputs/Day-by-Day-Itinerary.md` 產出完整每日行程，每個項目用 wikilink 連回 wiki 裡的原始筆記（保留細節，不要重複貼落一次全部內容）
4. 對於 `status` 還是 `researching` 或 `shortlisted` 的項目，主動詢問使用者是否要納入或捨棄，不要自己擅自決定

## 語言與風格

所有筆記、index 頁面統一用繁體中文書寫，符合家人閱讀習慣。摘要語氣簡潔、資訊導向，不需要文學化描述。

## 使用者的個人註記（重要）

使用者會直接在 `wiki/` 裡的筆記加自己的想法。有兩種情況：

1. **針對特定筆記的註記** — 每則筆記結尾都有一個 `## 📝 我的備註` 區塊。這個區塊**你絕對不能修改、刪除、或覆蓋**，即使這則筆記因為有新素材需要更新其他部分。更新筆記時，永遠保留這個區塊原樣，把新內容加在這個區塊**之前**。如果某則筆記還沒有這個區塊，建立筆記時要主動加上（內容留空即可，讓使用者自己填）。
2. **跨主題、不屬於任何特定筆記的雜想** — 放在 `personal/` 資料夾。這個資料夾跟 `raw/` 一樣，你**完全不會讀取、不會處理、也不會拿裡面的內容去產生 wiki 筆記**，純粹是使用者自己的空間。

`wiki/分類瀏覽/` 底下的 index 頁面因為每次都會整份重寫，**不適合**用來寫個人註記，如果使用者想在瀏覽篩選頁時看到自己的補充，請提醒他改在對應的單一筆記裡寫，或放進 `personal/`。

## 絕對規則

- 不修改 `raw/` 內容
- 不修改、不讀取 `personal/` 以及 `noteGarage/` 內容
- 不刪除任何筆記，除非使用者明確要求
- 不刪除、不覆蓋任何筆記裡的 `## 📝 我的備註` 區塊
- 衝突資訊一律標記，不擅自判斷取捨
- Index 頁面永遠整份重寫以保持一致，不要手動局部編輯造成格式漂移
